# 数据整理与清洗方案（2026-08-10）

> 目标：暂停功能开发，先做数据层治理——去重、合并、瘦身、自动化校验，降低占用、优化加载性能、提升后续开发效率。

## 二、分阶段执行

### 阶段 0：数据资产清单（先做）

写一个扫描脚本 `tools/audit-data.py`，输出每份数据的：大小、记录数、字段、被哪些 html/js 引用、重复 key 数。以此作为后续每阶段的前后对比基线。

### 阶段 1：去重与死数据清理

1. `library-2025.js` 移入 `data-src/` 归档（保留源文件，不进发布包）。
2. `photo-candidates.js` 只在 docs 照片挑选页使用——主站不再加载，docs 页面改成相对路径直引。
3. 校名/专业名归一化：全半角括号、校区写法（如「哈尔滨工业大学（深圳）」）、空格统一；消除跨文件 key 不一致（这是合并的前提）。
4. `library-2026.js` 按 (院校代码, 专业代码) 查重，重复行合并计划数/备注；与 lines-* 交叉核对，删除无投档线且无计划的孤儿行。
5. `school-meta.js` 内部多来源同 key 字段冲突时按「官方 > 权威媒体 > 网友整理」优先级保留并标注来源。

### 阶段 2：按域合并

- 生成脚本 `tools/build-data.py`：读 data-src/ 与各源文件 → 输出合并后的 `data/*.js`（保持 `window.GK_*` 全局名不变，改 js 层引用点最少）。
- 院校 10 文件 → `GK_SCHOOLS`；专业 4 文件 → `GK_MAJOR_DB`；排名 5 文件 → `GK_RANKS`；评估 2 文件 → `GK_ASSESS`；lines 6 文件 → `GK_LINES`。
- 预估：去掉重复 key 与字段冗余后，data/ 体积 34MB → 约 22MB（未压缩）。
- **口径不变**：lines 合并仅改存储，逻辑仍默认 2026、不做跨年混算（README 既有口径声明保持不变）。

### 阶段 3：瘦身与构建压缩

1. 删除 js 层未读取的字段（以 audit 脚本的字段引用清单为准，逐个确认）。
2. 已有数据多数是紧凑数组，无需重排；主要省在去重和合并。
3. 构建产物双轨：开发态保留可读源（`data/src/`），发布态产出 `data.bundle.min.js`（整体）+ 按需分片（transfer / school-intro 长尾 / whitepaper 独立 chunk）。
4. 目标：线上首屏脚本体积从 34MB 降到 10MB 以内（配合 gzip 后实际传输可再降 70%+）。

### 阶段 4：校验自动化

- `tests/data-integrity.py`：唯一性（校名/专业名/代码）、必填字段、跨文件引用一致性、年份口径标注检查（缺标注的文件在构建时报错）。
- 每次构建数据后自动跑一遍，index.html 与 index-beta.html 的引用清单保持同步（当前两页清单已一致，纳入 CI 式检查）。
- docs 内嵌工具（照片挑选、白皮书生成）涉及的数据路径同步更新。

## 三、风险与纪律

- **先建基线**：动手前先 git 提交当前 data/ 状态（含 docs 未提交文件），保证任何阶段可回退。
- **每阶段独立提交**：清理/合并/压缩各一次提交，改动大时保留旧文件到 `data-src/` 或 `archive/` 再删。
- **生成优先**：合并后的数据一律由 `tools/build-data.py` 产出，不手改产物；源数据留在 data-src/。
- **不改业务逻辑**：本次只动数据层与加载方式，不顺手改功能；js 层引用只做改名与懒加载改造。
